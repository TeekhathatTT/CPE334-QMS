## 1. Purpose and Scope

The Queue and Service Management System (QMS) supports a service counter or restaurant by replacing informal queue coordination with a persistent, auditable, role-based workflow. Sprint 1 delivers the minimum usable vertical slice: authentication, authorization, queue discovery, customer queue registration, queue-number assignment, customer status lookup, and operator lifecycle control. The system is designed for browser-based use, an HTTP API, relational storage, and seed data for local verification.

Included in Sprint 1:
- authenticated CUSTOMER and OPERATOR roles
- queue catalog and queue availability rules
- customer join workflow and private status reads
- queue-number generation and FIFO processing
- operator actions to call, start, and complete service
- transactional integrity and access-control validation

Excluded from Sprint 1:
- customer self-registration
- password reset
- cancellation and no-show workflows
- multiple counters or priority queue logic
- analytics and appointment booking

### 1.1 Sprint 2 additions (rev. 2.0)

F-07 (Customer cancellation and queue withdrawal, Issue #40) adds to Sprint 2:
- a customer may cancel their own `WAITING` entry; the entry becomes the terminal status `CANCELLED` with a server-generated `cancelledAt` time and is kept for history
- a cancelled entry is not active, so the customer may join the same queue again and receives a new queue number

Still excluded after rev. 2.0:
- leaving a `CALLED` or `SERVING` entry, and no-show handling (F-08) (*rev. 3.0:* no-show handling is added by F-08, §1.2; a customer still cannot leave a `CALLED` or `SERVING` entry themselves)
- operator-initiated cancellation, and reinstating a cancelled entry
- multiple counters, priority queues, analytics and appointment booking (F-09–F-12)

Feature design: [features/sprint-2-f07-customer-cancellation.md](./features/sprint-2-f07-customer-cancellation.md).

### 1.2 Sprint 2 additions (rev. 3.0)

F-08 (No-show handling and recovery, Issue #41) adds to Sprint 2:
- an assigned operator may mark a `CALLED` entry as `NO_SHOW` when the customer does not come to the counter; the server records `noShowAt` and counts the no-show in `noShowCount`
- an assigned operator may return (recover) a `NO_SHOW` entry to the queue **once**; it becomes `WAITING` again at its **original FIFO position** (its `joinedAt` and queue number do not change) and `recoveredAt` is recorded
- a second no-show of the same entry is final: it cannot be returned again
- a `NO_SHOW` entry is not active, so the customer may also join the same queue again with a new number

Still excluded after rev. 3.0:
- an automatic no-show timer or grace period (the operator decides)
- customers marking themselves as no-show or returning themselves to the queue
- a configurable recovery limit, a per-event audit log, and no-show analytics (F-11)
- multiple counters, priority queues and appointment booking (F-09, F-10, F-12) (*rev. 4.0:* multi-counter support is added by F-09, §1.3)

Feature design: [features/sprint-2-f08-no-show-recovery.md](./features/sprint-2-f08-no-show-recovery.md).

### 1.3 Sprint 2 additions (rev. 4.0)

F-09 (Multi-counter support, Issue #42) adds to Sprint 2:
- named service counters (`OPEN` / `CLOSED`) belonging to a `ServiceQueue`, provisioned via deterministic idempotent dev/test seed data (`Counter 1`, `Counter 2` per seeded queue) and a dedicated idempotent counter-only provisioning script/migration for Cloud SQL / production
- operator endpoints to list a queue's counters (`GET /api/operator/queues/{queueId}/counters`), toggle counter status (`PATCH /api/operator/counters/{counterId}/status`), and call the next eligible `WAITING` entry for a specific `OPEN` counter (`POST /api/operator/counters/{counterId}/call-next`)
- concurrency-safe multi-counter claiming (`Counter` row lock + `QueueEntry` `FOR UPDATE SKIP LOCKED`) so parallel calls across counters never double-claim the same entry
- additive `counterId` and `counterName` fields on every serialized `QueueEntry` payload, displayed on both the operator queue workspace and the customer's ticket when `CALLED` or `SERVING`
- backward-compatible preservation of legacy `POST /api/operator/queues/{queueId}/call-next` (`counterId = NULL`, `204 No Content` when empty) and clearing `counterId` alongside `calledAt` when an entry is recovered from `NO_SHOW` (F-08)

Still excluded after rev. 4.0:
- runtime admin CRUD to create, rename, or delete counters, or UI to assign specific operators to counters
- priority queue routing and counter skill matching (F-10) (*rev. 5.0:* priority queue policy is added by F-10, §1.4; counter skill matching remains excluded)
- per-counter analytics and wait/service-time reporting (F-11)
- advance appointment booking (F-12)

Feature design: [features/sprint-2-f09-multi-counter.md](./features/sprint-2-f09-multi-counter.md).

### 1.4 Sprint 2 additions (rev. 5.0)

F-10 (Priority queue policy, Issue #43) adds to Sprint 2:
- a two-level `QueuePriority` enum (`NORMAL`, `PRIORITY`) on `QueueEntry`, defaulting to `NORMAL` on customer join
- priority-aware FIFO ordering (`PRIORITY` before `NORMAL`, then `joinedAt ASC, id ASC`) extending BR-01 across both counter-scoped Call Next (F-09) and legacy queue-level Call Next (F-05), operator entry listing, and customer `aheadCount` calculation
- an operator-only endpoint (`PATCH /api/operator/queue-entries/{entryId}/priority`) allowing an assigned operator to change a `WAITING` entry's priority between `NORMAL` and `PRIORITY`, while rejecting non-`WAITING` entries with `409 INVALID_STATE_TRANSITION`
- server-enforced prevention of customer self-elevation: `POST /api/queues/{queueId}/entries` always creates `NORMAL` entries and rejects any non-`NORMAL` `priority` payload with `403 FORBIDDEN` (and rejects customer calls to the priority-update endpoint with `403 FORBIDDEN`)
- additive `priority` field on every serialized `QueueEntry` payload, displayed with an operator toggle (enabled only for `WAITING` entries) on `/operator/queues/:id` and as a read-only badge on customer ticket/detail views
- cross-feature preservation of `priority` when an operator recovers a `NO_SHOW` entry back to `WAITING` (F-08) and concurrency-safe claiming across parallel F-09 counters (`FOR UPDATE SKIP LOCKED`)

Still excluded after rev. 5.0:
- automatic time-based anti-starvation priority aging (Sprint 2 uses manual operator priority adjustment only so ordering stays deterministic and testable; automatic aging is deferred as a future enhancement)
- customer-requested or self-elevated priority tiers, or multi-level (> 2) priority schemes
- counter skill matching or priority-dedicated counter routing
- operational analytics and wait/service-time reporting (F-11)
- advance appointment booking (F-12)

Feature design: [features/sprint-2-f10-priority-queue-policy.md](./features/sprint-2-f10-priority-queue-policy.md).

### 1.5 Sprint 3 additions (rev. 6.0)

**F-11 Operational analytics (issue #44; to be implemented test-first for the 29 November checkpoint after this contract is approved).** It adds:
- A read-only operator report for one assigned queue over an inclusive date range (`GET /api/operator/queues/{queueId}/analytics?from=YYYY-MM-DD&to=YYYY-MM-DD`). Dates are interpreted in `Asia/Bangkok` (UTC+07:00) and the range is at most 31 days.
- Metrics computed from the lifecycle timestamps the system already keeps (BR-11, FR-13):
  - **volumes** by current status of the entries that joined in the range
  - **waiting time** (`joinedAt` → `calledAt`)
  - **service time** (`serviceStartedAt` → `completedAt`)
  - a per-day breakdown
- An operator analytics page at `/operator/queues/:id/analytics`.

There is no schema change. Customers and operators who are not assigned to the queue are denied.

**F-12 Advance appointment booking (contract only at the checkpoint; implementation due 13 December).** It adds:
- Appointment slots per queue (start, end, capacity), created and closed by an assigned operator.
- Customer booking of a slot inside a booking window (at least 60 minutes and at most 14 days ahead), owner-only cancellation before the slot starts, and owner-only check-in (from 15 minutes before to 15 minutes after the slot start). Check-in creates a `WAITING` queue entry with system-assigned `PRIORITY`.
- Capacity and double-booking prevention enforced in PostgreSQL transactions with row locks and a partial unique index.

**F-13 Product hardening and launch readiness (contract only at the checkpoint; implementation due 13 December).** It adds:
- HTTP security headers (NFR-09).
- Login throttling with `429 RATE_LIMITED` (FR-31, NFR-10).
- An accessibility scan of the core screens (NFR-11).
- Full E2E on Chromium, Firefox and WebKit (NFR-12).
- Structured request logs, a backup check and a rehearsed rollback (NFR-13).
- A launch checklist (FR-32): full regression and performance re-run on the release candidate, Lab 6 UAT re-tests closed, and no open Major or Critical defect.

Still excluded after rev. 6.0:
- exporting analytics (CSV/PDF), charts, cross-queue or organisation-wide dashboards, and per-counter or per-operator performance rankings
- recurring or bulk slot creation, waitlists for full slots, reminders or notifications (email/SMS/push), and payment
- customer self-registration, password reset, and multi-factor authentication
- automatic priority aging (still deferred from rev. 5.0)

## 2. Concrete Stakeholder Problem

Customers often stand near the service counter waiting for attention, but they cannot reliably tell how many people are ahead of them or how long they may still have to wait. When queue information is unclear or the calling process is inconsistent, customers may hesitate to leave the waiting area because they fear missing their turn, and they may become frustrated and lose confidence in the service experience. This is especially disruptive in busy service environments where the waiting line is not visible to everyone and where customers are expected to remain nearby while they wait.

Operators must often manage queues manually or by informal communication, and they can easily become confused about serving order. A queue may be skipped, called incorrectly, or processed in a conflicting order when multiple customers believe they are next. Without a reliable shared record of queue state, operators can accidentally call the wrong person and create a dispute or service delay. The organization therefore lacks a consistent way to coordinate customer flow and maintain trust in the service process.

For management, inconsistent queue handling reduces customer confidence and weakens the quality of service. Without reliable queue records it is difficult to measure waiting time and service time, identify bottlenecks, or assess whether staffing and service processes are working effectively. A centralized queue management system is needed to provide a single, auditable source of truth for queue state, clear customer communication, and disciplined operator action.

## 3. Actors and Permissions

| Actor | Allowed | Enforcement |
|---|---|---|
| Anonymous | login only | no access to protected endpoints |
| CUSTOMER | login/logout, list OPEN queues, join an OPEN queue, read own entry, cancel own `WAITING` entry (rev. 2.0), list bookable slots, book, cancel and check in own appointments (rev. 6.0) | no operator actions, cannot set or raise own queue priority (rev. 5.0), no access to other customers' private entries |
| OPERATOR | login/logout, view assigned queues, view queue entries, call next, start, complete, mark a `CALLED` entry no-show, return a `NO_SHOW` entry to the queue (rev. 3.0), list queue counters, open/close counters, call next for an `OPEN` counter (rev. 4.0), update priority (`NORMAL` ↔ `PRIORITY`) of `WAITING` entries (rev. 5.0), read analytics for assigned queues, create, list and close appointment slots and view their appointments (rev. 6.0) | must be assigned to the target queue (and match `Counter.assignedOperatorId` if set) |
| Provisioning seed | create users, queues, and operator assignments | no runtime interactive access |

Access control is enforced on every request: role, ownership, and queue assignment must be checked before API actions are executed. A customer looking up another customer's entry must receive the same `404 RESOURCE_NOT_FOUND` response as a nonexistent entry. An authenticated operator without an assignment to the target queue must receive `403 FORBIDDEN`.

## 5. Business Rules and Decisions

| ID | Rule | Decision and rationale |
|---|---|---|
| BR-01 | Priority-aware FIFO processing for eligible `WAITING` entries: `PRIORITY` entries before `NORMAL` entries, with deterministic FIFO tie-breaking `(joinedAt ASC, id ASC)` within each priority level (rev. 5.0, F-10) | **Rev. 5.0:** extends Sprint 1 pure FIFO with an explicit 2-level priority sort key (`CASE WHEN "priority" = 'PRIORITY' THEN 0 ELSE 1 END ASC, "joinedAt" ASC, "id" ASC`). When all `WAITING` entries have `NORMAL` priority, ordering is identical to Sprint 1 FIFO. (Sprint 1 text kept in §11 Revision history.) |
| BR-02 | Queue numbers are positive integers scoped to a single service queue | Avoids collisions across different queues; numbers are unique within one queue during the queue lifecycle |
| BR-03 | Number generation is protected at the database layer using a transactional row lock | Prevents duplicate numbers under concurrent join requests; application pre-checks are insufficient alone |
| BR-04 | Queue numbers do not automatically reset in Sprint 1 | Keeps the queue-number contract deterministic and avoids service-day ambiguity |
| BR-05 | One active entry per customer per queue; active = `WAITING`, `CALLED`, `SERVING` | **Rev. 3.0:** `COMPLETED`, `CANCELLED` and `NO_SHOW` entries are not active, so the customer may join that queue again and receives a new, larger queue number (BR-02, BR-04). Returning a `NO_SHOW` entry to the queue makes it active again, so it is rejected while the customer has another active entry in that queue (BR-16). The database partial unique index is unchanged. (Sprint 1 and rev. 2.0 text in §11.) |
| BR-06 | A customer may hold at most 2 active queue entries (`WAITING`, `CALLED`, or `SERVING`) across all queues simultaneously, and at most one active entry per customer per queue (BR-05). Attempting to join a 3rd `OPEN` queue while holding 2 active entries is rejected with `409 MAX_ACTIVE_ENTRIES_REACHED`. | Prevents queue hoarding across counters while allowing customers to participate in up to two distinct service flows simultaneously. Entries that are not active (`COMPLETED`, `CANCELLED` from rev. 2.0, `NO_SHOW` from rev. 3.0) do not count toward the 2-entry limit (Updated 2026-11-27, Issue #51). |
| BR-07 | One queue entry belongs to one customer and one queue; customer reads are self-scoped and operators scope through assigned queues | Prevents cross-customer and cross-queue leakage |
| BR-08 | Queue availability is `OPEN` or `CLOSED`; only `OPEN` queues appear in the customer join catalog | Makes availability testable and consistent with the queuing workflow |
| BR-09 | Valid lifecycle is `WAITING -> CALLED -> SERVING -> COMPLETED`, plus `WAITING -> CANCELLED` by the owning customer (rev. 2.0), plus `CALLED -> NO_SHOW` and `NO_SHOW -> WAITING` (once per entry) by an assigned operator (rev. 3.0) | No other alternate transitions or repeats are allowed. `COMPLETED` and `CANCELLED` are terminal. `NO_SHOW` is terminal once `noShowCount` is 2, or once the entry can no longer be returned. (Sprint 1 and rev. 2.0 text in §11.) |
| BR-10 | `Call Next` on an empty queue returns `204 No Content` and performs no state change | Defines the empty-queue case without raising a workflow error. **Rev. 4.0:** applies to the legacy queue-level endpoint (`POST /api/operator/queues/{queueId}/call-next`); counter-scoped Call Next (`POST /api/operator/counters/{counterId}/call-next`) returns `409 NO_WAITING_ENTRIES` with no state change (BR-19). (Original text in §11.) |
| BR-11 | Lifecycle timestamps are server-generated UTC values written atomically with the status change | Ensures consistent history and testability |
| BR-12 | Transactions and database constraints enforce uniqueness and state invariants | Reduces race conditions and guarantees consistent results |
| BR-13 | Only the customer who owns an entry may cancel it, and only while it is `WAITING`. The queue's availability (`OPEN` or `CLOSED`) does not matter. Cancelling a `CALLED`, `SERVING`, `COMPLETED` or already `CANCELLED` entry is rejected with `409 INVALID_STATE_TRANSITION`; a repeated cancel is not an idempotent success. A non-owner receives `404 RESOURCE_NOT_FOUND`; a non-customer role receives `403 FORBIDDEN`. (rev. 2.0, F-07) | A customer must always be able to leave the line. A called customer who leaves is a no-show (F-08), and service in progress is the operator's to end. Privacy follows BR-07 / AD-07. |
| BR-15 | Only an operator assigned to the entry's queue may mark it `NO_SHOW`, and only while it is `CALLED`. There is no grace period: the operator may mark it at any time after the call. The queue's availability does not matter. Marking a `WAITING`, `SERVING`, `COMPLETED`, `CANCELLED` or already `NO_SHOW` entry is rejected with `409 INVALID_STATE_TRANSITION`. An unassigned operator receives `403 FORBIDDEN`; a customer (including the entry's owner) receives `403 FORBIDDEN`; an unknown entry returns `404 RESOURCE_NOT_FOUND`. (rev. 3.0, F-08) | The operator is the one who sees whether the customer came. A timer would need a clock policy this system does not have. Customers cannot mark themselves (issue #41). |
| BR-16 | Only an operator assigned to the entry's queue may return a `NO_SHOW` entry to the queue, and only while `noShowCount` is 1. The entry becomes `WAITING` with its original `joinedAt` and queue number, so it is next in FIFO order among the entries that joined after it; `calledAt` is set to `NULL` and `recoveredAt` is recorded. **Rev. 4.0:** `counterId` is also set to `NULL` on return (BR-20). **Rev. 5.0:** the entry's existing `priority` (`NORMAL` or `PRIORITY`) is preserved on return (BR-23). If the entry is called and marked `NO_SHOW` again (`noShowCount` 2), a return is rejected with `409 RECOVERY_LIMIT_REACHED`. A return of a non-`NO_SHOW` entry is rejected with `409 INVALID_STATE_TRANSITION`. If the customer already has another active entry in the same queue, the return is rejected with `409 DUPLICATE_ACTIVE_ENTRY`. **Rev. 4.5:** if the customer already holds 2 active entries across all queues (BR-06), the return is rejected with `409 MAX_ACTIVE_ENTRIES_REACHED`; the entry stays `NO_SHOW` with `noShowCount` 1, so it can still be returned once a slot is free. The same-queue check comes first, as on join. The queue's availability does not matter. (rev. 3.0, F-08; rev. 4.0, F-09; rev. 4.5, BR-06; rev. 5.0, F-10) | A late customer gets one more chance at the place they already had, without a new number, and a repeat no-show does not block the line forever. BR-05 must still hold, so a customer who rejoined keeps the new entry. Clearing `counterId` ensures the next Call Next records the newly calling counter. Preserving `priority` keeps a priority customer's tier intact when staff return them to the line. A return makes the entry active again, so it must respect the same cross-queue cap as a join (BR-06, rev. 4.5). |
| BR-17 | `NO_SHOW` is not active. A `NO_SHOW` row is never deleted, is never eligible for Call Next, keeps its queue number, is **shown** in the operator entry list (so it can be returned), stays visible in the customer's own reads, and is not counted in any `aheadCount`. Each status change and its server-generated UTC timestamp (`noShowAt`, `recoveredAt`) and `noShowCount` are committed atomically. `noShowCount` is between 0 and 2, enforced by a database `CHECK` constraint. `noShowAt` holds the time of the latest no-show. (rev. 3.0, F-08) | Keeps history (FR-13), the FIFO rule (BR-01) and BR-11; makes the recovery limit hold in the database, not only in code. |
| BR-14 | `CANCELLED` is a terminal status. The status change and the server-generated UTC `cancelledAt` are committed atomically in one conditional update. A cancelled row is never deleted, is never eligible for Call Next, keeps its queue number (never reused), is excluded from the operator entry list, and is not counted in any `aheadCount`. (rev. 2.0, F-07) | Keeps history (FR-13) and the FIFO rule (BR-01) intact, and makes cancel and Call Next mutually exclusive on the same entry (BR-12, NFR-03). |
| BR-18 | A `ServiceQueue` may have zero or more named `Counter` records (`(serviceQueueId, name)` unique), each with status `OPEN` or `CLOSED` (default `OPEN`) and an optional `assignedOperatorId` referencing an `OPERATOR` user. Only an operator assigned to `counter.serviceQueueId` may list counters for that queue or toggle a counter's status; if `assignedOperatorId` is non-null, only that operator may toggle or call next on that counter (`403 FORBIDDEN` otherwise). Counter creation and deletion are provisioned by seed data rather than runtime CRUD in Sprint 2. (rev. 4.0, F-09) | Keeps multi-counter permissions aligned with AD-08 while allowing per-counter operator scoping when needed without adding admin CRUD scope. |
| BR-19 | **Scope: counter-scoped Call Next (`POST /api/operator/counters/{counterId}/call-next`).** Allowed only when `counter.status` is `OPEN`; calling on a `CLOSED` counter is rejected with `409 COUNTER_CLOSED`. It atomically locks the `Counter` row (`FOR UPDATE`), selects the next eligible unlocked `WAITING` entry in `counter.serviceQueueId` ordered by priority-aware FIFO (`CASE WHEN "priority" = 'PRIORITY' THEN 0 ELSE 1 END ASC, "joinedAt" ASC, "id" ASC`, rev. 5.0; previously `"joinedAt" ASC, "id" ASC`) with `FOR UPDATE SKIP LOCKED LIMIT 1`, and commits `status = CALLED`, `calledAt = clock_timestamp()`, and `counterId = counter.id`; if no `WAITING` entry exists, it returns `409 NO_WAITING_ENTRIES`. Closing a counter blocks only future Call Next on that counter; entries already `CALLED` or `SERVING` at that counter retain their `counterId` and may still be started, completed, or marked no-show. Parent queue availability (`OPEN`/`CLOSED`) is not checked (consistent with AD-05). **Rev. 4.1:** Retaining the legacy queue-level endpoint (`POST /api/operator/queues/{queueId}/call-next`) without counter `OPEN`/`assignedOperatorId` checks is an explicitly accepted backwards-compatibility trade-off solely to preserve unmodified Sprint 1 / F-07 / F-08 regression suites (deprecation/removal deferred to a future sprint); legacy Call Next explicitly writes `counterId = NULL`, uses the same priority-aware FIFO ordering (rev. 5.0), and keeps `204 No Content` when empty (BR-10). (rev. 4.0, rev. 4.1, rev. 5.0, F-09/F-10) | Guarantees deadlock-free, double-claim-free parallel service across counters while allowing in-flight customers to finish when a counter closes and keeping Sprint 1 / F-07 / F-08 regression suites intact. |
| BR-20 | `QueueEntry.counterId` is nullable and enforced at the database layer (BR-12) by a PostgreSQL composite foreign key `FOREIGN KEY ("counterId", "serviceQueueId") REFERENCES "Counter"("id", "serviceQueueId") ON DELETE RESTRICT ON UPDATE RESTRICT` (`MATCH SIMPLE`, default), backed by `UNIQUE ("id", "serviceQueueId")` on `Counter`. `MATCH SIMPLE` allows `counterId IS NULL` while strictly rejecting any non-null `counterId` belonging to a different `serviceQueueId` and preventing `Counter.serviceQueueId` updates while referenced. Every serialized `QueueEntry` includes additive `counterId` (`string \| null`) and `counterName` (`string \| null`). Entries in `WAITING` or `CANCELLED` always have `counterId = NULL`. When a `NO_SHOW` entry is returned to `WAITING` (BR-16), `counterId` is cleared to `NULL` alongside `calledAt`. Legacy queue-level Call Next explicitly writes `counterId = NULL`. (rev. 4.0, rev. 4.1, rev. 4.3, F-09) | Enforces same-queue counter integrity at the database level while preserving full backward compatibility with Sprint 1, F-07, and F-08 tests and letting customer views display the counter name directly without extra API calls. |
| BR-21 | Priority levels use a two-value enum `QueuePriority`: `NORMAL` (default on every newly created `QueueEntry`) and `PRIORITY`. Customers cannot set or elevate their own priority: on `POST /api/queues/{queueId}/entries`, request-body `priority` validation runs **before** any database lookup (`404`/`409`), after auth, role, and CSRF checks—omitted/empty body or literal `{"priority":"NORMAL"}` proceeds to create a `NORMAL` entry (`201`), `{"priority":"PRIORITY"}` is rejected with `403 FORBIDDEN`, and malformed/unknown `priority` values are rejected with `400 INVALID_ARGUMENT`. Any `CUSTOMER` request to `PATCH /api/operator/queue-entries/{entryId}/priority` is also rejected with `403 FORBIDDEN` (enforced server-side, never UI-only). (rev. 5.0, rev. 5.1, F-10) | Prevents customers from self-promoting in line, guarantees deterministic request validation before DB lookups, and keeps Sprint 1 empty-body join requests 100% backward compatible. |
| BR-22 | Only an `OPERATOR` assigned to the entry's queue may update `QueueEntry.priority` (no `ADMIN` role exists in `Role`), and only while `QueueEntry.status === WAITING` (parent queue `availability` is not checked, per `AD-05`). Attempting to change priority on a `CALLED`, `SERVING`, `COMPLETED`, `CANCELLED`, or `NO_SHOW` entry is rejected with `409 INVALID_STATE_TRANSITION`. Setting the same priority (`NORMAL -> NORMAL` or `PRIORITY -> PRIORITY`) on a `WAITING` entry is idempotent (`200 OK`) and leaves `joinedAt` and `queueNumber` unchanged. **Anti-starvation rule (Sprint 2):** manual operator priority adjustment only; automatic time-based priority aging is explicitly out of scope for Sprint 2 (**known limitation:** continuous `PRIORITY` arrivals/promotions can starve `NORMAL` entries unless an operator intervenes manually; rev. 5.1). (rev. 5.0, rev. 5.1, F-10) | Keeps priority changes scoped to active waiting entries managed by responsible staff and ensures deterministic, repeatable ordering without clock-dependent aging heuristics. |
| BR-23 | Ordering and cross-feature consistency: (a) SQL queries order waiting entries using an explicit sort key (`CASE WHEN "priority" = 'PRIORITY' THEN 0 ELSE 1 END ASC, "joinedAt" ASC, "id" ASC`) so `PRIORITY` always precedes `NORMAL` regardless of PostgreSQL enum declaration order; (b) both F-09 counter-scoped Call Next and legacy queue-level Call Next apply this ordering under `FOR UPDATE SKIP LOCKED`; (c) `GET /api/operator/queues/{queueId}/entries` applies priority ranking **only to `WAITING` entries** (`CASE WHEN "status" = 'WAITING' AND "priority" = 'PRIORITY' THEN 0 ELSE 1 END ASC, "joinedAt" ASC, "id" ASC`), preserving strict chronological `joinedAt ASC, id ASC` ordering for non-`WAITING` statuses (`CALLED`, `SERVING`, `NO_SHOW`, `COMPLETED`) so active and historical lists are never distorted by priority (rev. 5.1); (d) `computeAheadCount` counts only `WAITING` entries strictly ahead under `(priority_rank ASC, joinedAt ASC, id ASC)`, meaning `aheadCount` for a `NORMAL` customer is non-monotonic and may increase when another waiting entry is promoted to `PRIORITY` (rev. 5.1); (e) F-08 `recoverNoShowEntry` preserves the entry's `priority` when returning `NO_SHOW -> WAITING`; (f) F-07 `cancelEntry` allows cancelling both `NORMAL` and `PRIORITY` `WAITING` entries and retains `priority` for history; (g) every serialized `QueueEntry` includes additive `priority` (`"NORMAL" \| "PRIORITY"`). (rev. 5.0, rev. 5.1, F-10) | Ensures every API read, `aheadCount` calculation, counter claim, and no-show recovery agrees on one unambiguous ordering policy while keeping non-`WAITING` history chronological and staying safe under concurrent multi-counter load. |
| BR-24 | **Analytics cohort (F-11).** A report covers the entries of queue Q whose `joinedAt` falls inside the requested range (BR-26), including `CANCELLED` and `NO_SHOW` entries. `volumes` counts these entries by their **current** status: `joined` (all), `waiting`, `called`, `serving`, `completed`, `cancelled` and `noShow`. It also counts `recovered` (`recoveredAt` not null) and `priority` (`priority = PRIORITY`). The status counts always add up to `joined`. | A cohort by join date makes every number reproducible from stored rows. It needs no new table and counts each entry exactly once. |
| BR-25 | **Duration metrics (F-11).** Each duration is a difference between two stored timestamps:<br>• **Waiting time** = `calledAt − joinedAt`, over cohort entries with `calledAt` not null (`CALLED`, `SERVING`, `COMPLETED`, and `NO_SHOW`). For an entry returned to the queue after a no-show, `calledAt` is the latest call (BR-16 clears it on return), so its waiting time includes the time before the no-show.<br>• **Service time** = `completedAt − serviceStartedAt`, over `COMPLETED` cohort entries.<br><br>Entries without the needed timestamps are counted in `volumes` but excluded from that metric. For each metric the report gives `count`, `averageSeconds`, `medianSeconds` (`percentile_cont(0.5)`), `p90Seconds` (`percentile_cont(0.9)`) and `maxSeconds`. Values are seconds, rounded to 1 decimal place. When `count` is 0, the other four values are `null`. | The definitions follow the lifecycle timestamps of BR-09 and BR-11. An empty range or incomplete entries give a defined result instead of an error or a division by zero. |
| BR-26 | **Range, timezone and access (F-11).**<br>• `from` and `to` are required calendar dates (`YYYY-MM-DD`), with `from ≤ to` and an inclusive span of at most 31 days. A violation returns `400 INVALID_ARGUMENT`.<br>• The range means `[from 00:00, to + 1 day 00:00)` in `Asia/Bangkok` (UTC+07:00, no DST). Timestamps stay stored in UTC (BR-11).<br>• `daily` has one row per calendar date in the range, including days with zero entries.<br>• Only an `OPERATOR` assigned to Q may read the report. A `CUSTOMER` gets `403 FORBIDDEN`, an unassigned operator gets `403 FORBIDDEN`, and an unknown queue gets `404 RESOURCE_NOT_FOUND` (same middleware as `GET .../entries`).<br>• The endpoint is a read (`GET`, no CSRF token) and never changes a row. | A fixed local timezone matches the service location and makes day boundaries testable. The 31-day cap keeps NFR-04 reads bounded. |
| BR-27 | **Appointment slots (F-12).** An `AppointmentSlot` belongs to one queue and has:<br>• `startsAt`, and `endsAt = startsAt + durationMinutes` (duration 15–120)<br>• `capacity` 1–20 (database `CHECK`)<br>• `status` `OPEN` or `CLOSED`<br><br>`(serviceQueueId, startsAt)` is unique (`409 DUPLICATE_SLOT`). Only an operator assigned to the queue may create or close a slot. A new slot must start at least 60 minutes in the future. A `CLOSED` slot takes no new bookings, but its existing appointments stay valid and can still be cancelled or checked in. Slots are never deleted. | This is the simplest scheduling model that supports capacity and booking windows without calendars or recurrence. |
| BR-28 | **Booking window (F-12).** A booking is allowed only while `startsAt − 14 days ≤ now ≤ startsAt − 60 minutes` (server clock, `clock_timestamp()` inside the booking transaction). Outside the window the result is `409 BOOKING_WINDOW_CLOSED`. A booking also needs the slot to be `OPEN` (`409 SLOT_CLOSED`) and the queue to be `OPEN` (`409 QUEUE_NOT_AVAILABLE`, as in AD-05). | The cutoff gives operators a stable list before each slot. The limit on booking ahead stops customers hoarding places. |
| BR-29 | **Capacity and double-booking (F-12).** The booking transaction locks the slot row (`FOR UPDATE`). It counts that slot's active appointments (`BOOKED` and `CHECKED_IN`) and rejects the booking with `409 SLOT_FULL` when the count has reached `capacity`. A customer may hold at most one active appointment per queue (`409 DUPLICATE_BOOKING`), checked under a lock on the customer's `User` row. The partial unique index `Appointment_active_customer_slot_uidx` on `(slotId, customerId) WHERE status IN ('BOOKED','CHECKED_IN')` is a database backstop. Lock order: `User` → `AppointmentSlot` → `Appointment`. | This keeps NFR-03 for bookings: concurrent requests can neither overbook a slot nor create two bookings for one customer. |
| BR-30 | **Ownership and cancellation (F-12).** Customers read, cancel and check in only their own appointments. Another customer's appointment returns `404 RESOURCE_NOT_FOUND` (AD-07). A `BOOKED` appointment can be cancelled by its owner while `now < startsAt`. After that the result is `409 BOOKING_WINDOW_CLOSED`. Cancelling a non-`BOOKED` appointment returns `409 INVALID_STATE_TRANSITION`. `CANCELLED` is terminal and frees the place. | This reuses the privacy and lifecycle conventions of F-04 and F-07. |
| BR-31 | **Check-in (F-12).** The owner may check in a `BOOKED` appointment while `startsAt − 15 min ≤ now ≤ startsAt + 15 min`. Outside that window the result is `409 CHECK_IN_WINDOW_CLOSED`. Check-in runs the join rules of BR-05, BR-06 and BR-08 (`409 DUPLICATE_ACTIVE_ENTRY`, `MAX_ACTIVE_ENTRIES_REACHED` or `QUEUE_NOT_AVAILABLE`, with the appointment unchanged). In one transaction it then:<br>• creates a `WAITING` `QueueEntry` with the next queue number and `priority = PRIORITY`, set by the system (see the BR-21 note)<br>• sets the appointment to `CHECKED_IN` with `checkedInAt` and `queueEntryId`<br><br>Lock order: `User` → `ServiceQueue` → `Appointment`, the same order as `joinQueue`. | Customers who booked ahead are served before walk-ins of the same tier, without letting customers choose their own priority. |
| BR-32 | **Appointment lifecycle (F-12).** `BOOKED → CANCELLED` (owner, before start) and `BOOKED → CHECKED_IN` (owner, inside the check-in window) are the only transitions. A `BOOKED` appointment whose check-in window has passed is reported as `MISSED`. This is a derived `effectiveStatus` computed when the appointment is read; it is not stored and no background job changes it. `MISSED` appointments do not count toward capacity for new bookings, because the slot has already started. | A derived status avoids a scheduler and keeps the stored state change-driven and auditable. |
| BR-33 | **Hardening policy (F-13).**<br>• Login throttle counters (FR-31) are stored in PostgreSQL. They work across Cloud Run instances and survive restarts. Keys are the normalized email and the client IP (first `X-Forwarded-For` hop, set by the Cloud Run front end).<br>• Request logs are one JSON line per request with `requestId`, `method`, route path (no query string), `status` and `durationMs`. They never include bodies, cookies, `Authorization`/CSRF headers, passwords or session IDs (NFR-01). | Throttling must hold under horizontal scaling. Logs must support incident review without leaking secrets. |

*Rev. 6.0 note (BR-21, F-12):* BR-21 still forbids customer self-elevation on `POST /api/queues/{queueId}/entries`. Appointment check-in (BR-31) is a separate, system-defined path. On that path the server, not the customer, sets `priority = PRIORITY` on the new entry. The customer cannot choose or change the value, and the check-in request has no `priority` field.

## 7. Error Handling and API Contract Summary

| Scenario | HTTP status | Error code |
|---|---|---|
| User is not authenticated | 401 | `UNAUTHORIZED` |
| Operator accesses a queue not assigned to them | 403 | `FORBIDDEN` |
| Customer attempts to access another customer's entry | 404 | `RESOURCE_NOT_FOUND` |
| Invalid queue state transition | 409 | `INVALID_STATE_TRANSITION` |
| Closed queue or duplicate active join | 409 | `QUEUE_NOT_AVAILABLE` or `DUPLICATE_ACTIVE_ENTRY` |
| Cross-queue active entry cap reached (2 active entries held) | 409 | `MAX_ACTIVE_ENTRIES_REACHED` |
| Invalid payload or malformed identifier | 400 | `INVALID_ARGUMENT` |
| Empty queue on Call Next | 204 | No body |
| Customer cancels an entry that is not `WAITING` (rev. 2.0) | 409 | `INVALID_STATE_TRANSITION` |
| Entry changed by another request during a cancel (rev. 2.0) | 409 | `CONCURRENT_MODIFICATION` |
| Operator marks no-show on an entry that is not `CALLED`, or returns an entry that is not `NO_SHOW` (rev. 3.0) | 409 | `INVALID_STATE_TRANSITION` |
| Operator returns an entry that was already returned once (rev. 3.0) | 409 | `RECOVERY_LIMIT_REACHED` |
| Operator returns an entry while the customer has another active entry in that queue (rev. 3.0) | 409 | `DUPLICATE_ACTIVE_ENTRY` |
| Operator returns an entry while the customer already holds 2 active entries across all queues (rev. 4.5, BR-06) | 409 | `MAX_ACTIVE_ENTRIES_REACHED` |
| Operator calls next on a `CLOSED` counter (rev. 4.0) | 409 | `COUNTER_CLOSED` |
| Operator calls next on an `OPEN` counter when no `WAITING` entries exist (rev. 4.0) | 409 | `NO_WAITING_ENTRIES` |
| Customer attempts to join with non-`NORMAL` priority or calls operator priority endpoint (rev. 5.0) | 403 | `FORBIDDEN` |
| Operator updates priority on an entry that is not `WAITING` (rev. 5.0) | 409 | `INVALID_STATE_TRANSITION` |
| Invalid `priority` payload on priority update or customer join (rev. 5.0) | 400 | `INVALID_ARGUMENT` |
| Analytics range missing, malformed, reversed or longer than 31 days (rev. 6.0) | 400 | `INVALID_ARGUMENT` |
| Customer or unassigned operator requests queue analytics (rev. 6.0) | 403 | `FORBIDDEN` |
| Booking a slot that has no capacity left (rev. 6.0) | 409 | `SLOT_FULL` |
| Booking a `CLOSED` slot (rev. 6.0) | 409 | `SLOT_CLOSED` |
| Operator creates a slot with a start time already used in that queue (rev. 6.0) | 409 | `DUPLICATE_SLOT` |
| Customer already holds an active appointment in that queue (rev. 6.0) | 409 | `DUPLICATE_BOOKING` |
| Booking outside the booking window, or cancelling after the slot started (rev. 6.0) | 409 | `BOOKING_WINDOW_CLOSED` |
| Check-in outside the check-in window (rev. 6.0) | 409 | `CHECK_IN_WINDOW_CLOSED` |
| Too many failed logins for an email or client IP (rev. 6.0) | 429 | `RATE_LIMITED` (with `Retry-After`) |

The `RESOURCE_NOT_FOUND` code is deliberately used for customer cross-owner lookup to avoid revealing whether that resource exists. A 404 is never used for unauthenticated requests. A 403 is never used to mask the privacy violation in the customer case.

## 8. Assumptions & Architectural Decisions

| ID | Topic | Final decision | Rationale | Affected docs |
|---|---|---|---|---|
| AD-01 | Authentication strategy | Session-based authentication using HTTP-only cookies with CSRF protection | Better fit for browser-based app flow, server-side invalidation, and simple testing against a single backend | SRS, system-sds, API spec |
| AD-02 | Database concurrency | Queue number generation and update logic occur inside a PostgreSQL transaction using row-level locking on the target queue row | Prevents duplicate numbers when multiple join requests are processed simultaneously | SRS, system-sds, tests |
| AD-03 | Sprint 1 scope cut | Customer self-registration and password reset are excluded; seed data initializes required test users and queues | Keeps Sprint 1 focused on the required vertical slice and avoids unsupported user-management features | SRS, features, API spec |
| AD-04 | Queue numbering | Positive integer queue numbers are unique within a service queue and never reset during Sprint 1 | Simple, testable, deterministic numbering without calendar or service-day complexity | SRS, system-sds, tests |
| AD-05 | Queue availability | `OPEN` / `CLOSED`; CLOSED queues reject new joins but existing entries may still be completed by assigned operators | Matches service-delivery needs without adding scheduling logic | SRS, system-sds, API spec |
| AD-06 | Duplicate prevention & active entry cap | At most one active entry per customer per queue (BR-05) and at most 2 active entries across all queues simultaneously (BR-06); entries that are not active (`COMPLETED`, `CANCELLED`, `NO_SHOW`) release a slot | Prevents same-queue double-booking and cross-queue hoarding while allowing fresh entries after completion (Updated 2026-11-27, Issue #51) | SRS, Feature SDS, system-sds, API spec, tests |
| AD-07 | Customer privacy | Return `404 RESOURCE_NOT_FOUND` for cross-owner lookups, matching the public behavior of a missing entry | Prevents leakage of private information through resource enumeration | SRS, API spec, tests |
| AD-08 | Operator permissions | Operators may only act on queues assigned to them | Ensures service workflow is scoped to real operational responsibility | SRS, system-sds, API spec |
